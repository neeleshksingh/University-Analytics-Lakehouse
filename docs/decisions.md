1. Why does PySpark need Java? ✅ Right idea. Fuller answer:

“Spark’s engine is written in Scala and runs on the JVM. PySpark is only a Python API: my Python code sends instructions to a Java process through a bridge called Py4J, and the JVM does the real work. So Java must be installed wherever PySpark runs locally. On Databricks it’s preinstalled.”

2. Why Postgres in Docker, but Spark native? We covered this earlier, so here’s the short version to remember:

“Postgres is a service: I start it once and leave it running, and Docker keeps it isolated and easy to reset. Spark code is what I edit and rerun constantly, so running it natively gives faster runs and easier debugging in VS Code. And since production is Databricks, not a container, a Spark container wouldn’t make local development any more realistic.”

Rule of thumb: services in Docker, code you’re actively writing runs natively.

3. .gitignore and .env. ✅ Correct. Add the why:

“Anything pushed to GitHub stays in the Git history forever, even if you delete it later, so a leaked password must be treated as compromised. .env holds secrets and machine-specific settings, so it’s ignored, and .env.example is committed instead to show which settings are needed, without real values.”

4. Why 5 files, and what is _delta_log?

“Spark splits data into partitions so it can work in parallel, and each partition writes its own file. With local[*], Spark created a partition per CPU core, so even 5 rows became several small files. Too many small files slows reads, which is why Delta has OPTIMIZE to compact them.”

“_delta_log is Delta’s transaction log. Every write adds a numbered JSON file listing which Parquet files were added or removed. Readers use the log to see a consistent version of the table, which gives Delta ACID transactions, MERGE, and time travel. Plain Parquet has no log, so it can’t do any of that.”

# Experiment

- I defined the schema once in SQLAlchemy, so the same code creates it in PostgreSQL locally and Azure SQL in the cloud. SQLAlchemy translates types like Boolean into BOOLEAN or BIT for each database.

# why is program_course unique on program_id + course_id, and not on course_id alone?

- A course can belong to many programs, so course_id alone isn’t unique. But the same course shouldn’t be added twice to the same program, so the combination program_id + course_id is unique. That’s a composite unique constraint on a many-to-many bridge table: program_course connects programs and courses.

# student_id (surrogate key) is a meaningless number generated by the database. roll_no (business key) is the identifier people use.

- We join on student_id because:

- Business keys can change. If the university changes its roll-number format, or corrects a wrong one, only the student row changes. Every attendance, exam and fee row still points to the same student_id. With roll_no as the key, you’d have to update millions of child rows.
- Integers are smaller and faster to join and index than strings like NIT22CSE0041.
- The business key stays unique (the unique=True on roll_no), so you never lose the human identifier.

# Why is there an index on updated_at in every table?

- Every incremental run asks for WHERE updated_at > last_watermark. Without an index, the database scans all 5 million attendance rows to find today’s few thousand. The index on updated_at lets it jump straight to the new rows, so each run’s cost depends on how much changed, not how big the table is.

# What would break in an incremental pipeline if rows were hard-deleted instead of using is_deleted?

- The pipeline only finds rows where updated_at is newer than the watermark. A hard-deleted row no longer exists, so no query can ever return it. The pipeline never learns it’s gone, and the lake keeps showing a student or payment that was deleted in the source. With a soft delete, deleting means setting is_deleted = true and updating updated_at, so the change flows through like any other update, and Silver can mark the row as deleted.

# Why define the schema in SQLAlchemy instead of writing SQL for each database? Give a concrete example of something that differs.

- PostgreSQL and SQL Server write the same thing differently: a boolean is BOOLEAN in Postgres but BIT in SQL Server, auto-numbering is GENERATED BY DEFAULT AS IDENTITY vs IDENTITY, timestamps are TIMESTAMP vs DATETIME. I defined the schema once in Python, and SQLAlchemy generates the right SQL for each database. The same code creates it locally in Postgres and in Azure SQL.

# Why does create_schema use engine.begin() (a transaction)?

- It’s all or nothing. If table 12 fails, tables 1–11 are rolled back too, so the database is never left half-built. I fix the error and rerun.

# You found a bug earlier that only appears on Azure SQL. What was it, and what does it teach about testing?

- Testing on one database doesn’t prove it works on another. Postgres is more lenient than SQL Server in places. So the schema has to be created on the real target, Azure SQL, before I trust it. That’s part of Phase 6.
